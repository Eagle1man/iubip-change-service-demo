Внедрение по приказу

Вся работа по заявкам на внесение изменений на сайт идёт через этот сервис.

Сотрудник выбирает раздел сайта из списка, заполняет одну форму и отправляет заявку. Ответственное лицо видит её в очереди и согласует либо возвращает — но только по формальному основанию. Почтовых писем и ручной сборки файлов больше нет.

Открыть демо Как это работает

Что закрыто требованиями приказа

  • Идентификатор блока не набирается руками — подставляется из реестра
  • Отказ — только по формальным основаниям, 8 кодов
  • Три уровня ответственности: Исполнитель, Ответственное лицо, администратор
  • Формат YAML собирается автоматически по Приложению 2
  • Срок считается сам: дата изменения + 10 рабочих дней − 3 рабочих дня

Зачем это нужно

До внедрения правки собирались вручную: сотрудник писал письмо, администратор подбирал идентификатор блока и вручную готовил файл. Ошибки всплывали уже на сайте, а спорить о причинах возврата было не с кем.

Было

  • Идентификаторы подбирались на глаз
  • Формат передачи — кто во что горазд
  • Возврат без объяснения основания
  • История изменений терялась в почте

Стало

  • Раздел выбирается из Перечня, поля подставляются сами
  • YAML собирается по шаблону приказа
  • Возврат с кодом основания из закрытого списка
  • Каждая заявка сохранена со статусом и историей

Кто участвует

  • Исполнитель — сотрудник, включённый в Перечень
  • Ответственное лицо — согласует и выдаёт пароли
  • Администратор сайта — публикует согласованное

Демонстрация

Полноценное интерактивное демо: вход, форма заявки, очередь согласования и готовый YAML-файл. Данные вымышленные, работает без сервера прямо в браузере.

▶ Открыть интерактивное демо

Пройти полный путь: от входа до согласованной заявки и готового файла.

Что показывает демо

  • Раздел выбирается выпадающим списком
  • id_block, url, selector недоступны для ввода
  • Возврат возможен только с одним из 8 кодов
  • На выходе — файл вида iubip_<id>_<дата>.yml

Как устроено

1

Сотрудник открывает сервис

Вход по тем же Ф.И.О., что в Перечне. Пароль выдаёт Ответственное лицо.

2

Выбирает раздел

В списке — только те разделы, которые за ним закреплены. Чужой раздел не открывается.

3

Заполняет форму

Действие, дата, причина и содержимое. Тип содержимого определяет блок, а не человек.

4

Отправляет

Сервис сам собирает YAML по Приложению 2 и кладёт заявку в очередь.

5

Ответственное лицо решает

Согласовать или вернуть с кодом основания. Содержательных причин в списке нет.

6

Администратор публикует

Скачивает готовый .yml и загружает его в систему сайта.

Правила, которые сервис не даёт нарушить

Идентификаторы подставляются, а не набираются

id_block, url, selector и block_path приходят из реестра и доступны только для чтения. Подбор идентификатора не входит в обязанности ни Исполнителя, ни администратора сайта.

Возврат — только формальный

В форме возврата нет свободного выбора причины: доступны ровно восемь кодов. Содержательное замечание — вне сервиса, выставить его нельзя.

F-01 форматF-02 имя файлаF-03 пустое поле F-04 раздел не найденR-01 нет в реестре R-02 расхождениеC-01 тип содержимогоC-02 нет файла

Срок считается сам

Дата изменения плюс десять рабочих дней минус три рабочих дня. Расхождение в сроках — предупреждение, а не отказ.

Пароли выдаёт Ответственное лицо

Одноразовый пароль работает один вход и требует немедленной смены. Электронная подпись при загрузке не требуется.

Статус разработки

ЭтапСодержаниеСостояние
1. Каркас и доступ База, вход, роли из Перечня, выдача паролей готово
2. Заявка и согласование Форма, очередь, коды отказа, сборка YAML готово
3. Реестр блоков Сканирование страниц сайта, заполнение url и selector ждёт доступа к сайту
4. Развёртывание Внутренняя площадка, контейнер, конфигурация ждёт площадку

Пока реестр не заполнен, заявки по неподтверждённым разделам получают отказ R-01. Это сделано намеренно: подставлять выдуманные адреса страниц сервис не будет.
